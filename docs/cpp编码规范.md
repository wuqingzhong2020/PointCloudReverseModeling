# ReverseModeling C++ 编码规范

适用范围：`ReverseModeling/` 与 `tests/` 中的工程自有 C++20 / Qt6 代码，以及配套 CMake 文件。当前构建入口提供 Windows / MSVC 2022 v143 / x64 预设；第三方库通过 `CMAKE_PREFIX_PATH` 与标准 CMake 包接入。

## 0. 使用说明

- 本文供开发人员与编码助手共同使用，规定当前工程的代码写法。用户当前明确要求优先，公共数据契约、线程归属和错误语义以实际接口为准。
- 规则默认用于新增和实质修改的代码，不据此批量改造无关旧代码。当前源码中的既有命名和局部格式可保留；序列化字段和公开接口名称不得因风格调整而改变。
- “必须 / 禁止”表示约束，“优先 / 建议”允许有依据的替代；`[待确认]` 按条目默认值执行，不据此扩大修改范围。规则编号保留，修订直接更新正文。
- 工程事实见 [主业务开发指南](../ReverseModeling/README.md)，配置、编译和运行入口见 [根 README](../README.md)，测试说明见 [tests/README.md](../tests/README.md)。
- 先确认职责、数据和生命周期，再检查输入、错误与并发，最后检查命名、排版和构建清单。第三方源码、SDK 配方及构建产物不作为业务源码改写。

## 1. 语言与工具链

- **TOOL-01 目标语言标准固定为 C++20**
  - 新增代码优先采用语义清楚、当前工具链支持的标准设施，如 `std::optional`、`std::span`、`std::jthread`、concepts 和 ranges；不降低标准，也不为使用新语法改写无关代码。
  - C++23 / C++26 功能不得仅因本机编译器支持就直接引入。

- **TOOL-02 当前构建基线为 Windows / MSVC v143 / x64**
  - 以根 `CMakePresets.json` 和 `cmake/common.cmake` 的配置为准，Windows 使用 VS 2022 v143、动态 CRT 和 C++20。
  - SDK 具备其他平台产物，不代表本应用已经完成对应平台的编译与运行验收。

- **TOOL-03 使用工程实际接入的 Qt6**
  - Qt 模块在 `cmake/Dependencies.cmake` 查找，版本由所选依赖安装前缀确定；当前项目不维护 Qt5 兼容分支。
  - 使用安装版本支持的公开 API，不导入其他工程的 Qt 私有兼容头、主题或插件设施。

- **TOOL-04 优先复用已有依赖**
  - 能由标准库、Qt、Eigen、PCL、OCCT 或既有业务接口完成的功能，优先复用。
  - 新依赖须说明用途、版本和分发要求，并在 `Dependencies.cmake` 统一查找；SDK 中安装了某个库，不等于本项目已接入该库。
  - 当前 Python 绑定尚未接入；后续使用 CPython / pybind11 时按 Python 规范和实际 SDK ABI 设计，不把 SDK 可用性写成产品已实现能力。

- **TOOL-05 平台验证与实际修改范围一致**
  - 当前提供 Windows 预设，默认针对相关 Release 目标做增量验证；Linux 等平台按实际交付目标评估。
  - 说明实际执行的平台、配置和用例，不将 SDK 的跨平台验证或静态分析结果当作本应用的运行结果。

## 2. 文件与编码

- **FILE-01 新增 C++ 源码使用 UTF-8 with BOM**
  - 新增 `.h/.cpp/.inc` 采用 UTF-8 with BOM；Python、CMake、Markdown 与 shell 文件采用 UTF-8 无 BOM，shell 使用 LF。
  - 修改既有文件保留其编码和换行，不顺手批量转换。MSVC 仍通过公共 CMake 选项启用 `/utf-8`。

- **FILE-02 新增文件必须有「文件描述」头**
  - 格式：

    ```cpp
    /*
     * 文件描述：
     * [此处描述文件当前作用]
     */
    ```

  - 要求：`.cpp` 的描述要具体详细（职责、关键流程、依赖边界）；`.h` 可简练；描述必须出现在文件前 12 行内。
  - 反例：只写「实现 xxx 类」；或把版权、作者、日期等无信息量内容当成描述。
  - 验证：修改范围内人工核对源码前 12 行中的「文件描述：」。

- **FILE-03 文件名按主要类型或职责命名**
  - 主要类型优先使用同名 `PascalCase` 文件；公共值类型集合和自由函数按职责命名，如 `Types.h`、`Geometry.h`、`PlateRecognition.cpp`。
  - `main.cpp` 与现有测试文件沿用当前名字，不新增 `Common2.h`、`test1.cpp` 等无职责名称。

- **FILE-04 按现有职责划分文件**
  - `core` 放公共数据；`geometry` 放点云和几何实现；`commands` 放任务、工程状态、参数策略与序列化；`workbench` 放 Qt 与显示适配。
  - 头文件与源文件放在同一功能目录，不恢复独立的 `include` / `src` 分层。入口 `main.cpp` 位于 `ReverseModeling/` 下。

- **FILE-05 不新增无边界的聚合头文件**
  - 直接包含所需契约，例如 `core/Types.h`、`commands/CommandService.h`；不通过一个大头文件同时引入 Qt、PCL、OCCT 等全部实现依赖。
  - `Geometry.h` 等明确的模块接口可保留，第三方实现细节尽量放在 `.cpp` 或 PImpl 中。

## 3. 头文件与包含

- **INC-01 头文件必须自包含**
  - 要求：每个头文件单独包含即可编译通过，不依赖「谁先包含了我」的隐含顺序。
  - 反例：头文件里按值保存 `QString` 成员却不包含 `<QString>`，靠上层 `.cpp` 的包含顺序混过去。

- **INC-02 新增头文件使用 `#pragma once`**
  - 要求：新增头文件一律用 `#pragma once`；既有头文件保持原有保护方式不变（宏保护的继续用宏保护），不做统一改造，也不在既有文件里更换保护方式。
  - 反例：把既有宏保护文件顺手改成 `#pragma once`；新增宏保护时用 `#ifndef _HEADER_H` 这类易重名或下划线开头的宏名。
  - 动机：`#pragma once` 由编译器按文件去重，不怕宏名重名与复制粘贴；既有文件保持原样可避免无关 diff 与漏改 `#endif`。

- **INC-03 头文件按来源与固定顺序分组**
  - 要求：新增或调整的 `#include` 按以下顺序排列：**C/C++ 标准库 → Qt 库 → 其它开源第三方库 → 厂商提供的 SDK 库 → 当前项目**。
  - 分块与空行：上述每一类各自构成一个独立的头文件块，相邻非空块之间必须留一个空行区分，不得混排或紧贴；同一块内头文件连续排列，优先按字母序。没有对应头文件的类别直接省略，不保留空块或叠加空行。
  - 自身头文件：`.cpp` 对应的自身头文件、生成的 `ui_*.h` 等均归入最后的「当前项目」组；无自身头的拆分实现将实际声明头归入其所属工程组，不另设自身头优先的例外。
  - 默认：标准库、Qt 与开源第三方库头文件使用 `<>`；厂商提供的 SDK 库头文件与工程内头文件使用 `""`，工程内头文件采用工程包含目录下的路径。第三方确有必要的包含顺序约束时保留并说明，不为排序产生任务外的批量改动。

- **INC-04 头文件优先前置声明**
  - 要求：仅以指针/引用出现且不要求完整类型时优先前置声明；继承、按值成员、内联实现及 Qt 元对象处理需要完整类型时直接包含。不要把类型别名或模板特化误声明为普通类。
  - 反例：为一个 `QWidget *` 成员就 `#include <QWidget>`，顺带拖入整条 Widgets 依赖链。

- **INC-05 包含路径大小写与磁盘一致，统一使用 `/`**
  - 要求：`#include "commands/CommandService.h"` 的大小写必须与磁盘文件名完全一致，分隔符只用 `/`。
  - 动机：Windows 大小写不敏感会掩盖错误，Linux 下直接编译失败。

- **INC-06 头文件中禁止 `using namespace`**
  - 头文件使用限定名或函数内部局部 `using`；实现文件中的命名空间引入限制在必要范围。
  - 不向 `std`、`Qt` 或第三方命名空间添加项目符号。

- **INC-07 不把实现细节暴露到公共头文件**
  - `core/Types.h` 保持中立值类型，避免向 `CommandService` 等业务契约泄露 PCL、TopoDS 或 AIS 对象。
  - Qt 显示适配可使用自己的必要 Qt/OCCT 类型；重量级实现优先前置声明或 PImpl。持有 `std::unique_ptr<Impl>` 时，析构等需要完整类型的成员在实现文件中定义。

- **INC-08 包含路径体现依赖来源**
  - 标准库与第三方库使用 `<>`；工程内头文件使用 `""`，路径相对于目标的包含根目录，如 `commands/CommandService.h`。
  - 优先链接 CMake 导出目标取得第三方包含目录，不拼接 SDK 私有布局，也不为缩短引用额外添加库内部目录。

## 4. 命名

- **NAME-01 类型名用 PascalCase**
  - 要求：`class CommandService`、`struct CloudData`、`enum class TaskState`；`enum class` 的枚举值同样 PascalCase（`TaskState::Succeeded`）。
  - 禁止：`cloud_data`、`CCommandService`、`task_state_t` 等其它风格。

- **NAME-02 明确区分封装状态与公开数据**
  - 新增封装类成员采用 `m_` + camelCase；修改既有类时沿用该类的命名，如已有 `impl_`、`state_` 不作任务外重命名。
  - 纯数据结构的公开字段使用 camelCase，如 `expectedRevision`、`originMm`、`solidCount`；序列化键沿用既有契约。

- **NAME-03 函数名用 camelCase，表达动作或查询含义**
  - 要求：动作使用动词，如 `submitImport()`；查询可用 `task()`、`project()`。布尔查询优先 `is/has/can/should`，也允许已有且语义准确的 `finished()`。
  - 边界：不为独立新 API 引入 `GetXxx`/`SetXxx` 风格；重写既有接口及 `on_<对象名>_<信号名>` 自动连接槽时保留契约名称。

- **NAME-04 局部变量用 camelCase，不加类型前缀**
  - 反例：`strName`、`iCount`、`pShape`；用 `name`、`count`、`shape` 即可。

- **NAME-05 常量命名** `[待确认]`
  - 默认沿用所在模块的既有写法；新增编译期常量使用 `constexpr`，不为常量命名批量重排旧代码。
  - 保留的待确认项：是否统一编译期常量为 PascalCase、局部常量为 `k` 前缀。确认前不宣称全工程已有统一命名。

- **NAME-06 命名空间与本项目保持一致**
  - 业务契约使用 `reverse`，界面使用 `reverse::workbench`；仅实现文件使用的辅助符号可放匿名命名空间。
  - 需要跨文件共享但不属于公开 API 的辅助符号可使用 `detail`；头文件不得使用匿名命名空间。

- **NAME-07 业务入口沿用服务与数据契约**
  - 新命令沿用 `submitXxx`、`TaskSnapshot`、`ProjectSnapshot` 的接口形态；不引入并行任务框架或未经定义契约的字符串调用入口。
  - 外部绑定和 Web 接口尚未接入，新增时需明确生命周期、参数、错误码和版本规则，不绕过业务服务直接修改内核对象。

- **NAME-08 缩写按单词和既有类型处理**
  - 使用 `PointCloud`、`CommandService`、`OccViewport`、`sourceIndex` 等能表达职责的名称，不自造 `WkMgr`、`TskChg` 一类缩写。
  - PCL、OCCT、AIS、JSON 等外部类型与字段保留各自既有名称。

## 5. 排版与格式

- **FMT-01 大括号换行（Allman）**
  - 要求：独立新增代码默认使用 Allman；修改既有函数时沿用其局部排版，不扩大格式化范围。既有源码存在多种风格，不宣称全工程已统一。

- **FMT-02 缩进 4 个空格、不使用 Tab；行宽上限 120 列**
  - 要求：缩进 4 个空格、不使用 Tab，新增代码行宽上限 120 列；超长路径、不可拆分字面量与签名等允许超出，不做机械截断。续行对齐参数列或缩进 4 的整数倍；不做跨语句的赋值、注释列对齐。

- **FMT-03 控制语句必须带大括号**
  - 要求：新增 `if`/`else`/`for`/`while`/`do` 的语句体一律加 `{}`，**不因语句体只有一行而省略**，也不设早退次数之类的阈值。修改既有函数时，未改动逻辑的既有单行早退保持原样，不扩大格式化范围。
  - 反例：多行语句体不加大括号；新增 `if (a) b(); else c();`、`if (!ptr) return;` 这类省略写法。

- **FMT-04 运算符与标点空格**
  - 要求：二元运算符两侧各一个空格；逗号、分号后加空格；新增代码中 `*`/`&` 紧贴变量名（`QObject *parent`、`const QString &text`）；既有函数的局部格式保持原样。
  - 禁止：`a*b`、`f(x ,y)`、`int* p` 这类不符合新增代码约定的写法。

- **FMT-05 空行用于分组，不用于凑行数**
  - 要求：逻辑段落之间一个空行；连续空行不超过一行；函数之间一个空行；文件末尾不堆积空行。

- **FMT-06 成员初始化列表一个成员一行**
  - 要求：`m_xxx(new Xxx)`、`m_yyy(yyy)` 逐行排列，成员声明顺序与初始化顺序保持一致。

- **FMT-07 不做手工列对齐** `[待确认]`
  - 范围：既有代码若有用空格对齐注释或赋值的写法，按所在位置保留。
  - 默认执行：新增代码不用空格对齐列，也不主动重排既有对齐代码。
  - 待确认：既有对齐代码是否统一重排（建议否，避免无关 diff）。

- **FMT-08 不提交与本次任务无关的格式化改动**
  - 要求：不整文件重排、不批量改空格/换行/引号风格；确有需要时单独作为一次改动并说明原因。
  - 动机：无关 diff 会掩盖真实改动，评审与回溯成本都会上升。

## 6. 现代 C++20 用法

- **MOD-01 空指针一律使用 `nullptr`**
  - 新增代码不使用 `NULL`、`0` 或 `Q_NULLPTR` 表示空指针；旧代码仅在相关修改范围内调整。

- **MOD-02 重写虚函数写 `override`，明确封闭扩展点时才写 `final`**
  - 要求：重写函数标记 `override`；`final` 表达禁止继续继承或重写的设计决定，不因当前没有派生类而自动添加。
  - 反例：漏写 `const` 导致签名不匹配、实际没有重写成功。

- **MOD-03 枚举用 `enum class`**
  - 要求：新增独立枚举用 `enum class`；继承第三方、C ABI 或既有位标志契约时保留其类型形态。禁止把新枚举值散落成宏或 `static const int`。

- **MOD-04 资源管理优先 RAII 与明确所有权**
  - 普通独占资源优先 `std::unique_ptr`；QObject 优先父子所有权。只读工程数据按现有契约使用 `std::shared_ptr<const T>`。
  - OCCT `Handle(...)`、PCL 智能指针及 C API 配套释放方式按库约定使用，不能再交由另一拥有型指针重复释放。
  - 裸指针只表达非拥有引用，并明确有效期；异步任务捕获的参数与对象必须持续有效到任务结束。

- **MOD-05 `const` 正确性**
  - 要求：不修改可观察状态的成员函数加 `const`；大对象只读参数优先 `const T &`，标量、枚举及轻量视图优先按值传递；函数需保存副本时可按值接收再移动。
  - 反例：因漏写 `const` 导致上层被迫 `const_cast`。

- **MOD-06 `auto` 的使用尺度**
  - 要求：唯一判断标准是**不让代码更难理解**。类型在同行已明确（`new`、`static_cast`、迭代器、`std::make_unique`）或类型名冗长时用 `auto`；OCCT/SDK 句柄、几何与数值类型等关键类型不用 `auto` 隐藏，需要表明是指针时写 `auto *`。
  - 边界：`auto` 通常按值推导；需要保留引用时显式写 `auto &` / `const auto &`。不要因 `auto result = compute();` 隐藏重要类型或无意复制引用结果。
  - 待细化：本条按后续出现的实际代码示例补充正反例，再收紧判定标准。

- **MOD-07 编译期常量用 `constexpr`，不再新增宏**
  - 要求：可编译期求值的常量、尺寸、字符串键用 `static constexpr` / `constexpr`；运行期常量用合适的 `const` 类型。宏保留用于条件编译、导出、Qt 元对象及必要兼容，不用宏代替普通常量。
  - 禁止：新增 `#define MAX_NUM 10` 这类宏常量。

- **MOD-08 复用现有业务与序列化设施**
  - JSON 使用 nlohmann_json 与 `commands/Json.*`，任务和工程状态通过 `CommandService` 维护，逐板识别结果由 `PlateRecognition` 提供；不得用经验板厚替代缺测结果。
  - 不手写字符串拼接 JSON，不在窗口里复制一套模型状态或默认参数算法；当前没有通用日志框架或主题服务，不编造已经存在的设施。

- **MOD-09 优先使用无额外拷贝、语义清晰的写法**
  - 要求：只读遍历优先范围 `for`，大元素用 `const auto &`、小标量可按值；需要索引或同步访问多个序列时可使用索引循环。多返回值优先具名结构体，沿用已有出参契约。
  - 边界：`std::optional` 表达合法的「无值」，不能单独代替需要失败原因的结果；字符串视图与借用类型遵守 MOD-13。

- **MOD-10 类型转换必须显式**
  - 要求：需要显式转换时按对象模型选用 `static_cast`、`qobject_cast` 或 `dynamic_cast`；普通安全隐式转换不必机械加 cast。向下转型检查前置条件或失败结果；窄化、浮点转整数前检查有限性、范围与舍入意图。
  - 边界：Qt 6 容器长度使用 `qsizetype` 等匹配类型，与 `int` / `size_t` 交互时检查范围；`static_cast` 本身不验证范围。
  - 禁止：C 风格强转 `(int)x`、`(AIS_Shape*)obj`。

- **MOD-11 异常在明确边界转换**
  - 几何与参数错误使用 `GeometryError` 等既有异常，保留可判定的错误码与说明；不要为统一风格把所有服务改成 `bool` 返回。
  - 后台任务边界把异常转换为 `TaskSnapshot` 的失败/取消状态，提交前校验错误由调用方处理。异常不得逃出 Qt 事件回调或未来的语言绑定边界。
  - 补充必要上下文，在有能力处理的边界报告错误，不每层重复输出同一错误。

- **MOD-12 必须检查返回值的函数标 `[[nodiscard]]`**
  - 要求：新增表示成败、资源所有权或错误结果且忽略会造成错误的函数标 `[[nodiscard]]`；不把普通布尔查询全部标为错误结果。有意丢弃结果须说明理由，不能用强制转换压掉实际失败。

- **MOD-13 借用视图与引用不得超过被引用对象的有效期**
  - 要求：`std::span`、`std::string_view`、`QStringView`、引用及迭代器不拥有数据；不得返回指向局部变量的视图，也不得跨容器变更保存失效引用。
  - 反例：把临时 `QString` 的视图或临时 `QByteArray::constData()` 指针保存到成员、延迟任务或 SDK；异步任务需保存自有副本或明确持有所有者。

- **MOD-14 适用时优先采用 C++20 新设施**
  - 算法与查询：优先使用表达清楚的 `std::ranges` 算法、`std::views` 和关联容器 `contains()`，减少手写迭代器拼接、临时容器和仅判断存在性的 `find() != end()`。
  - 模板与接口：模板约束优先使用 concepts / `requires`，避免为同一目的新增复杂的 `enable_if` 或检测惯用法；连续内存的非拥有型参数优先考虑 `std::span`，并遵守 MOD-13 的生命周期约束。
  - 编译期表达：适用时使用 `constexpr`、`consteval`、`constinit`，分别表达可编译期求值、必须编译期求值，以及静态或线程存储期对象的常量初始化要求；不混淆三者语义。
  - 边界：选用新设施仍须满足当前工具链、可读性、性能和现有接口契约；不单为使用新语法而改变接口 ABI、数据所有权或重写无关代码。

## 7. Qt 与业务边界

- **QT-01 QObject 派生类按实际元对象需求声明**
  - 需要本类信号、槽、属性或元对象转换能力时添加 `Q_OBJECT`，并在对应 CMake 目标启用所需的 AUTOMOC；普通继承不等于必须新增该宏。
  - 构造函数使用合适的 `explicit` 和父对象参数，QObject / QWidget 子对象默认由父对象释放。提前销毁考虑线程归属，必要时使用 `deleteLater()`。

- **QT-02 信号槽只用新式语法**
  - 要求：静态已知连接用 `connect(sender, &Sender::signal, receiver, &Receiver::slot)` 或带 context 的 lambda 重载；重载信号显式消歧。
  - 禁止：为静态已知连接新增 `SIGNAL()`/`SLOT()` 写法；确需运行时动态元对象调用时沿用明确契约，不误改为无法表达的静态连接。

- **QT-03 跨线程只通过信号槽或明确同步交互**
  - 要求：工作线程不直接操作 `QWidget`；跨线程向 QObject 投递操作使用接收者线程的队列机制。检查连接类型、事件循环、参数元类型与生命周期，不用 `DirectConnection` 绕过线程归属。
  - 反例：工作线程里执行 `ui->label->setText(...)`。

- **QT-04 跨生命周期回调明确持有对象**
  - 信号连接的 lambda 优先提供接收 context；独立任务捕获的裸指针不因值捕获而延长生命周期。
  - `QPointer` 仅用于 QObject 的存活检查，不能替代跨线程同步；点云、模型、网格使用只读快照或稳定 ID。
  - 窗口关闭时取消并等待服务任务结束，定时器和回调不能继续访问已销毁的窗口或已替换的数据。

- **QT-05 容器与字符串选择**
  - 要求：与 Qt API 交互用 `QString`/`QList`/`QVector`/`QVariantMap`；纯算法内部可用 `std::vector`/`std::string`，但转换点要明确，不在循环里反复 `toStdString()`。
  - 禁止：为「更标准」把既有 Qt 容器整片替换成 STL 容器（会产生大面积无关改动）。

- **QT-06 区分界面文字与机器标识**
  - 当前界面新增中文文字优先 `QStringLiteral`；如果后续引入翻译，按完整的翻译资源与装载方案统一接入。
  - `objectName`、资源路径、JSON 键、命令名、错误码和配置键保持稳定，不对机器标识使用翻译函数。

- **QT-07 依赖通过明确入口传入**
  - 新增业务服务优先通过构造参数、函数参数或已有窗口/服务状态对象注入，不为访问方便引入单例与服务定位器。

- **QT-08 窗口通过命令服务访问业务**
  - `workbench` 负责交互、参数校验提示和显示；耗时几何任务通过 `CommandService` 提交。
  - `core`、`geometry` 和后台任务不依赖 QWidget 或操作 AIS 场景；显示适配在 GUI 线程把中立点云/网格转换为显示对象。
  - 当前没有插件 ABI 或动态插件系统，不引入其他工程的接口头和插件生命周期假设。

- **QT-09 UI 文件与生成物**

## 9. 错误处理与日志

- **ERR-01 沿用本项目明确的错误契约**
  - 几何接口使用 `GeometryError::code()` 和异常文本；异步任务通过 `TaskState`、`errorCode`、`message` 报告结果。
  - 正常缺省状态使用 `std::optional`；不能把失败转换为没有原因的空对象，也不改成其他工程的 `bool + QString &` 接口。

- **ERR-02 不得吞掉错误**
  - 要求：失败必须传递给有能力处理的调用方或边界；日志用于补充诊断，不能仅记录后继续返回成功。异常传播遵守 MOD-11，避免各层重复记录同一错误。
  - 反例：`catch (...) {}`；忽略 `bool` 返回值继续往下走；失败后返回默认对象。

- **ERR-03 外部输入先校验再创建业务对象**
  - 文件、界面参数、JSON 及未来脚本输入需检查大小、点数、索引、类型、有限性、单位、坐标系和几何约束；Release 同样执行校验。
  - 点云导入、模型构建先在局部结果中完成校验，成功后提交快照；失败保留原工程。导出沿用拒绝覆盖与临时写出后提交的策略。

- **ERR-04 不用默认值、单位变换或空对象掩盖错误**
  - 反例：读取失败时返回 `0` 或默认位姿，让上层以为读到了有效数据。
  - 要求：内部返回明确错误原因；不擅自改动公开 API 的既有错误语义。

- **ERR-05 日志** `[已废弃]`
  - 原因：本工程尚未规定统一日志框架，本条不参与检查；编号保留，不再复用。
  - 后续：将来需要约束日志时，另行确认后修订本条或新增条目。

- **ERR-06 用户提示与诊断信息各有用途**
  - 用户提示说明操作、失败原因和可采取的下一步；错误码保持稳定，技术上下文用于任务信息或诊断输出。
  - 不在几何层直接弹窗，不将错误仅打印到控制台后仍返回成功。

## 10. 并发、资源与性能

- **PERF-01 GUI 线程不执行耗时计算和 I/O**
  - 点云导入、建模、STEP 和偏差任务由服务工作线程执行；GUI 使用定时器查询状态和更新显示。

  - 保持当前单任务服务约定，忙时返回明确错误；不要因引入线程池而让多个 OCCT 操作同时修改同一模型。
  - 共享状态由明确所有者持有并同步；工作线程不得直接修改 UI 或让未完成结果对外可见。

- **PERF-03 避免隐式拷贝**
  - 要求：大对象只读时按 `const &` 传递；只读遍历 Qt 隐式共享容器时使用 const 访问，必要时用 `std::as_const` 避免 detach。写入仍使用正常可变访问。

- **PERF-04 Eigen 对齐和向量化与实际 SDK ABI 一致**
  - 当前工程通过公共设置定义 `EIGEN_MPL2_ONLY`；不照搬其他工程固定 16 字节对齐的宏或未经核对的 SIMD 选项。
  - 变更对齐、指令集或跨库 Eigen 类型时，核对 SDK 的构建定义、分配方式与 ABI，不在个别源码内单独定义 `/arch:AVX2`、`-mavx2` 或对齐宏。

- **PERF-05 第三方重对象生命周期集中管理**
  - 要求：OCC/VTK/PCL 的重对象由明确所有者持有并复用，避免循环内反复创建销毁；OCC 对象遵循 `Handle(...)` 引用语义。

- **PERF-06 缓存与全局状态有明确所有者**
  - 新缓存说明键、失效条件和线程模型。大点云、网格尽量共享只读快照，避免每次轮询重新复制。
  - 不引入依赖先后执行的可变全局注册器或“当前选中对象”式算法输入。

  - 优先可复现的配置、增量编译和定向测试，不因文档里列了命令就扩展到 SDK 重编译、打包或发布。

- **AI-05 按问题选择检索位置**
  - 优先读取本工程相关源码；依赖或运行问题可只读核对实际 SDK 配方、包配置和必要的构建输出，不做无目标的大范围递归扫描。

- **AI-06 结论要有依据**
  - 要求：说明改了哪些文件、依据哪几行代码、验证到什么程度；不确定就写「待确认」，不猜测、不编造 API 或行为。

- **AI-07 区分现有实现与目标规范**
  - 既有代码尚未遵循新写法时按本次修改范围处理，不宣称全工程已经符合；接口变更、平台扩展和新增偏好需说明依据与影响。

## 16. 追加与修订规则

**追加**：直接说「加一条：……」即可。AI 负责把它写进对应章节末尾、分配下一个编号，并按「要求 / 反例 / 动机」补全；跨章节的规则放到最贴切的类别下。

**修订**：保留编号，直接更新正文为当前有效要求；旧表述由 Git 历史追溯，不在正文同时保留两条相反要求。

**废弃**：保留编号并标记 `[已废弃]`，写清替代规则或废弃原因；编号不复用，废弃条目不再参与检查。新增尚未认可的偏好使用 `[待确认]`，不得自行转成「已确认」。

**模板**：

```markdown
- **类别-序号 一句话规则标题** `[待确认]`
  - 要求：必须 / 禁止 / 优先 ……
  - 反例：……（AI 常犯写法）
  - 动机：……（为什么这样取舍）
  - 关联：脚本或文档路径
```

**取舍原则**：只写「可判定」的规则（能指出某处代码符合或违反），不写「代码要优雅」这类无法执行的口号；一条规则只讲一件事。
